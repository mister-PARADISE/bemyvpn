# Наш userspace-TCP упирался в 6 Мбит/с. Виноваты были 16 бит из 1981 года — и ещё пять вещей

> **Площадка:** Хабр. Хабы: `Rust`, `Сетевые технологии`, `Высокая производительность`, `Open source`.
> **Формат:** Кейс/Разбор. **Ориентировочно:** ~18 000 знаков.
> **Обложка:** график «до/после» либо схема окна TCP.
>
> Это самостоятельная статья: её можно читать без первой. Публиковать лучше
> **второй**, через 5–10 дней после архитектурной — она тяжелее и уже.

---

Короткая версия для тех, кто торопится: мы взяли хороший userspace TCP/IP-стек,
воткнули в VPN, и он поехал со скоростью факса. Дальше две недели разбирательств,
шесть исправлений и рост пропускной способности в разы. Ни одно из шести не
работало по отдельности — и это главное, что я хочу рассказать.

Контекст в одном абзаце: мы делаем [BeMyVPN](https://github.com/mister-PARADISE/bemyvpn) —
P2P-VPN, где выходной точкой становится компьютер обычного человека. Ключевое
решение архитектуры: **хост не требует прав администратора**. Он не поднимает TUN
и не трогает `iptables`, а разбирает IP-пакеты гостя userspace-стеком и открывает
наружу обычные сокеты. Стек — форк [`ipstack`](https://github.com/narrowlink/ipstack),
хорошая асинхронная реализация на Rust.

Цена этого решения — TCP теперь наш. Со всеми последствиями.

## Симптом

`iperf3` через туннель на канале, где напрямую честные 100+ Мбит/с, показывал
единицы мегабит. Причём картина была характерная: **скорость почти не зависела от
ширины канала, но обратно зависела от пинга.** На локалхосте — прекрасно. На VPS
в соседней стране — грустно. На VPS за океаном — вообще никак.

Кто хоть раз ловил это, уже поставил диагноз. Для остальных — формула, ради которой
стоило начинать:

```
Пропускная способность ≤ Окно приёма / RTT
```

Это фундаментальный потолок: отправитель не может держать в полёте больше
неподтверждённых байт, чем ему разрешил приёмник. Разрешил 64 КБ при RTT 80 мс —
получите:

```
65535 байт / 0.08 с ≈ 819 КБ/с ≈ 6.5 Мбит/с
```

Шесть с половиной мегабит. При любом канале. Хоть гигабит — упрётесь в 6.5.

Откуда 64 КБ? Из RFC 793, 1981 год. Поле `Window` в заголовке TCP — **16 бит**.
Больше 65535 туда физически не влезает.

## Заплатка 1981 года: RFC 7323 Window Scaling

Проблему заметили быстро, и в 1992 году появился RFC 1323 (сейчас 7323) — опция
`Window Scale`. Идея бухгалтерски простая: в SYN стороны обмениваются «сдвигами», и
дальше все window-поля читаются как `значение << shift`. Сдвиг 7 — окна умножаются
на 128, потолок становится 8 МБ.

Опция согласуется **только в SYN/SYN-ACK**, ровно один раз, и только если её прислали
обе стороны. Прислали не оба — масштаба нет вообще.

В апстримном `ipstack` этой опции не было. Совсем. Что для стека, живущего внутри
локального туннеля, вполне разумно — там RTT околонулевой, и 64 КБ хватает с
запасом. У нас же RTT — это реальная сеть между двумя случайными людьми.

Реализация в форке — вот она целиком, и она правда небольшая:

```rust
// BeMyVPN fork: window scaling (RFC 7323). Если пир прислал wscale в
// SYN — принимаем его сдвиг и отвечаем своим (иначе оба сдвига 0 и
// поведение байт-в-байт как у оригинала). Свой сдвиг подбираем так,
// чтобы приёмный буфер целиком влезал в 16-битное window-поле.
if tcp.syn {
    let peer_shift = tcp.options_iterator().flatten().find_map(|o| match o {
        TcpOptionElement::WindowScale(s) => Some(s),
        _ => None,
    });
    if let Some(peer) = peer_shift {
        let mut ours: u8 = 0;
        while ours < 14 && (config.read_buffer_size >> ours) > u16::MAX as usize {
            ours += 1;
        }
        tcb.set_window_shifts(peer, ours);
        log::debug!("wscale negotiated: peer shift {peer}, our shift {ours}");
    }
}
```

Свой сдвиг не берётся с потолка: подбирается минимальный, при котором приёмный
буфер целиком влезает в 16 бит. Буфер 1 МБ → сдвиг 5. Меньше сдвиг — часть буфера
пир просто не увидит; больше — потеряем точность на округлении.

Дальше две функции-переводчика:

```rust
/// Эффективное окно пира В БАЙТАХ (raw-поле × 2^shift). До рукопожатия
/// shift=0 → в SYN поле не масштабируется, как велит RFC.
pub(super) fn get_send_window(&self) -> u32 {
    (self.send_window as u32) << self.snd_wnd_shift
}
```

Размер окна выбран не на глаз, а из BDP — произведения пропускной способности на
задержку:

```rust
/// Размер TCP-окна userspace-стека. Потолок потока = окно/RTT, поэтому окно
/// должно покрывать BDP пути (100 Мбит при RTT 80мс ≈ 1 МБ).
fn tcp_window() -> u32 { /* ... */ 1024 * 1024 }
```

Запустили. Стало **хуже**.

## Почему стало хуже: congestion control отсутствовал как класс

Оригинальный стек отправлял в сеть **сразу всё окно приёмника**. Пока окно было
64 КБ, это сходило с рук: 64 КБ одним всплеском переварит любой буфер по дороге.

А теперь представьте то же поведение с окном в мегабайт. Соединение открывается —
и мгновенно, без разгона, в сеть выплёскивается мегабайт. Буферы на пути
переполняются, начинается массовая потеря, дальше ретрансмиты, дальше ещё потери.
Классический congestion collapse, описанный Джекобсоном в 1988 году, воспроизведён
в 2025-м в отдельно взятом форке.

Никакого окна перегрузки в апстриме не было. Вообще. Пришлось добавить:

```rust
/// BeMyVPN fork: примитивный контроль перегрузки (slow start + AIMD).
/// Оригинал слал СРАЗУ всё окно (с wscale — мегабайты одним взрывом) →
/// переполнение буферов пути → массовая потеря → коллапс. cwnd начинается
/// с 16×MSS, удваивается за RTT (slow start) до ssthresh, дальше +MSS за
/// окно (congestion avoidance); при потере — деление пополам.
cwnd: u32,
ssthresh: u32,
```

Рост — учебниковый, но с одной деталью: считаем по свежеподтверждённым **байтам**,
а не по числу ACK. Иначе приёмник, дробящий подтверждения, разгонял бы нас
непропорционально быстро.

```rust
fn grow_cwnd(&mut self, ack: SeqNum) {
    if ack <= self.cwnd_acked { return; }
    let newly = ack.distance(self.cwnd_acked);
    self.cwnd_acked = ack;

    if self.cwnd < self.ssthresh {
        // slow start: +байт за байт = удвоение за RTT
        self.cwnd = self.cwnd.saturating_add(newly);
    } else {
        // congestion avoidance: +MSS за окно
        self.cwnd = self.cwnd.saturating_add((mss.saturating_mul(newly) / self.cwnd.max(1)).max(1));
    }
    self.cwnd = self.cwnd.min(self.max_unacked_bytes.max(mss));
}
```

И теперь в полёте держим минимум из трёх ограничителей — своего лимита, окна пира
и окна перегрузки:

```rust
let limit = self.max_unacked_bytes.min(self.get_send_window()).min(self.cwnd);
```

Стало лучше. Но не настолько, насколько должно было.

## Баг 3: приёмное окно, которое никогда не закрывалось

Дальше — мой любимый. Одна строчка, и она стоила больше всех остальных.

В функции, вычисляющей наше объявляемое окно, стояло примерно следующее:

```rust
avail.max(self.mtu)   // ← вот это
```

То есть: «объяви свободное место в буфере, но **не меньше одного MTU**».

Смысл понятен — защита от silly window syndrome, не объявлять микроскопические
окна. Последствие — катастрофическое: **наше приёмное окно никогда не достигало
нуля.** А значит, обратной связи по приёмнику не существовало вовсе.

Что происходит на практике. Гость льёт данные быстрее, чем хост успевает
перекладывать их в реальные сокеты. Правильное поведение TCP: приёмник объявляет
окно всё меньше, доходит до нуля, отправитель останавливается. Backpressure.

У нас же приёмник **всегда** говорил «места хватает, шли ещё». Очередь наверх
(unbounded, разумеется) росла. Память ела. А как только доходило до потерь —
всё разваливалось.

Починка:

```rust
/// BeMyVPN fork: раньше здесь стоял `avail.max(self.mtu)` — окно НИКОГДА не
/// закрывалось, то есть обратной связи по приёмнику не существовало вовсе:
/// быстрый гость лил во весь канал, а очередь наверх (unbounded) росла.
/// Теперь окно честно доходит до нуля. По RFC 1122 §4.2.3.3 (silly window
/// syndrome на приёмнике) объявляем либо ноль, либо хотя бы сегмент —
/// дробных окон пир не увидит. Порог берём min(MTU, буфер/2), иначе при
/// read_buffer_size < MTU окно залипло бы в нуле навсегда.
pub(super) fn get_recv_window(&self) -> u16 {
    let avail = self.get_available_read_buffer_size();
    let threshold = (self.mtu as usize).min(self.read_buffer_size / 2).max(1);
    if avail < threshold {
        return 0;
    }
    // `.max(1)`: место есть, значит объявлять ноль НЕЛЬЗЯ — пир ушёл бы в
    // persist навсегда (мы бы отвечали нулём на каждый зонд).
    (avail >> self.rcv_wnd_shift).try_into().unwrap_or(u16::MAX).max(1)
}
```

Два подводных камня здесь стоят внимания, потому что оба ведут к **вечному
зависанию соединения**, а не к замедлению:

1. **Порог `min(MTU, буфер/2)`, а не просто MTU.** Если `read_buffer_size` окажется
   меньше MTU, условие `avail < MTU` истинно всегда, окно залипает в нуле навсегда.
2. **`.max(1)` в конце.** Место есть, но после сдвига округлилось в ноль — и мы
   объявляем ноль. Пир уходит в persist-режим, шлёт зонды, мы на каждый отвечаем
   нулём. Соединение мертво, при том что буфер пуст.

Оба случая — не гипотетические, оба ловятся тестом:

```rust
assert!(tcb.get_recv_window() > 0, "пустой буфер → окно открыто");
// ...забиваем очередь наверх...
assert_eq!(tcb.get_recv_window(), 0, "очередь наверх забита, а окно всё ещё открыто");
// ...разгружаем...
assert!(tcb.get_recv_window() > 0, "окно обязано открыться обратно");
```

## Баг 4: fast retransmit, который молчал

Теперь про потери. В TCP есть два способа узнать, что пакет пропал: дождаться
таймаута (RTO — сотни миллисекунд, иногда секунды) или получить три дублирующих
ACK и ретрансмитнуть сразу (fast retransmit). Второй на порядок быстрее, и именно
он делает TCP пригодным для жизни на лёгких потерях.

В оригинале dup-ACK определялся так: пришёл ACK с тем же номером **и с тем же
значением окна**.

Второе условие убивает всё. На реальном трафике приёмное окно пира гуляет почти на
каждом ACK — приложение то забирает данные, то нет. Совпадение окна байт-в-байт —
редкость. Значит, dup-ACK почти никогда не распознавался, значит fast retransmit
де-факто не работал, значит **любая потеря ждала полный RTO**.

Одна потеря на жирном канале — и полсекунды тишины.

```rust
} else if self.seq != rcvd_ack && self.is_duplicate_ack_count_exceeded() {
    // BeMyVPN fork: dup-ACK определяется кумулятивным ACK'ом (тот
    // же ack, без данных, есть неподтверждённое), а НЕ равенством
    // окна. Прежнее условие `get_send_window_raw()==rcvd_window`
    // ГЛУШИЛО fast-retransmit на реальном трафике, где приёмное
    // окно пира гуляет почти на каждом ACK → любая потеря ждала
    // полный RTO. Само окно обновляется отдельно (update_send_window).
    PacketType::RetransmissionRequest
}
```

Признак потери и обновление окна — две разные вещи, и их нельзя было связывать.

## Баг 5: fast recovery, который резал окно в пол

Починили распознавание dup-ACK — и немедленно получили новую беду.

На жирном канале одна потеря порождает **целое окно** dup-ACK'ов: приёмник шлёт по
дубликату на каждый пришедший сегмент после дырки. Сотни штук. А обработчик на
каждом честно делил `cwnd` пополам.

Сто дубликатов — сто делений. Окно схлопывалось в пол (4·MSS) от **одного**
потерянного пакета. Разгон с нуля после каждой мелкой потери.

Правильное поведение — один сигнал перегрузки на **событие потери**, а не на
пакет. Это классический recovery-guard из NewReno:

```rust
/// BeMyVPN fork: войти в fast-recovery ОДИН раз на событие потери.
/// `true` → первый dup-ACK-триггер (снизить cwnd и ретрансмитить);
/// `false` → уже восстанавливаемся (cwnd повторно НЕ режем).
pub(crate) fn enter_fast_recovery(&mut self) -> bool {
    if self.in_recovery { return false; }
    self.in_recovery = true;
    self.recover = self.seq; // все данные, отправленные ДО потери
    self.on_congestion();
    true
}
```

Выход — когда кумулятивный ACK перешагнул отметку `recover`, то есть подтвердилось
всё, что было отправлено до потери. Следующая потеря снова снизит окно — ровно
один раз.

## Баг 6: RTO из константы

Последнее. Таймаут ретрансмита был фиксированной конфигурационной константой.
Одно значение на локалхост с RTT 0.2 мс и на трансатлантический путь с RTT 200 мс.
Слишком маленький — ложные ретрансмиты и лишняя нагрузка; слишком большой —
полсекунды простоя на каждой потере.

Добавили адаптивный RTO по RFC 6298 — сглаженный RTT плюс учетверённая вариация:

```rust
/// BeMyVPN fork: замер RTT по свежеподтверждённому НЕретрансмитнутому сегменту
/// (алгоритм Карна — ретрансмиты пропускаем, их RTT неоднозначен) и пересчёт
/// RTO по RFC 6298.
match self.srtt {
    None => { self.srtt = Some(rtt); self.rttvar = rtt / 2; }
    Some(srtt) => {
        let delta = if srtt > rtt { srtt - rtt } else { rtt - srtt };
        self.rttvar = self.rttvar.mul_f64(0.75) + delta.mul_f64(0.25);
        self.srtt = Some(srtt.mul_f64(0.875) + rtt.mul_f64(0.125));
    }
}
let srtt = self.srtt.unwrap_or(rtt);
self.rto = (srtt + 4 * self.rttvar).clamp(MIN_RTO, MAX_RTO);
```

Отдельно отмечу **алгоритм Карна** (1987) — из замера исключаются ретрансмитнутые
сегменты. Причина: получив ACK на сегмент, отправленный дважды, вы не знаете, какую
из двух отправок он подтверждает. Померите не то, испортите оценку, а испорченная
оценка RTO — это либо шторм ложных ретрансмитов, либо секундные паузы.

## Что из этого следует

Главный вывод не про TCP. Он про то, что **эти шесть исправлений не работают по
отдельности, а некоторые по отдельности делают хуже**:

- Window scaling **без** congestion control → мегабайтные всплески и коллапс.
  Первая правка сама по себе ухудшила ситуацию.
- Congestion control **без** починенного dup-ACK → окно растёт, но любая потеря
  стоит полный RTO.
- Починенный dup-ACK **без** recovery-guard → окно режется в пол от одной потери.
- Всё вышеперечисленное **без** закрывающегося приёмного окна → нет backpressure,
  память течёт, а на потерях всё разваливается.

TCP — это не набор независимых фич, а один механизм с обратными связями. Выдёргивать
из него куски по одному — способ две недели ходить по кругу, что мы и делали.

Второй вывод — практический, для тех, кто берёт userspace-стек в свой проект.
Такие стеки обычно пишутся и тестируются в условиях «локальный туннель, RTT
околонулевой, потерь нет». Там **все шесть** описанных проблем невидимы: окна 64 КБ
хватает, congestion collapse не наступает, потерь нет вовсе, RTO неважен. Стек
работает идеально — ровно до момента, когда между пирами появляется настоящая сеть.

Так что если вы тащите userspace TCP в продакшен через реальный интернет, проверьте
по списку: масштаб окна, окно перегрузки, закрывается ли приёмное окно до нуля,
живой ли fast retransmit, режется ли cwnd один раз на потерю, адаптивен ли RTO.

## Оговорка про числа

Формула `окно / RTT` даёт **теоретический потолок**, и 6.5 Мбит/с при 64 КБ и
80 мс — это именно она. Реальные замеры зависят от пути, потерь, времени суток и
настроения провайдера, так что относитесь к любым «выросло в N раз» осторожно — к
моим тоже. Что можно утверждать твёрдо: до правок потолок задавался окном и не
зависел от ширины канала, после — задаётся каналом.

Форк лежит в `vendor/ipstack/`, все правки помечены комментарием `BeMyVPN fork:` —
`git log` и `grep` покажут ровно то, что описано выше, включая тесты на каждый
случай.
