# Хост без root: VPN, в котором выходной точкой становится чужой компьютер

> **Площадка:** Хабр. Хабы: `Информационная безопасность`, `Rust`, `Сетевые технологии`, `Open source`, `Децентрализованные сети`.
> **Формат:** Туториал/Кейс. **Ориентировочно:** ~20 000 знаков.
> **Обложка:** схема «хост ↔ гость, координатор в стороне» из README.

---

Обычный VPN устроен так: вы платите сервису, сервис ставит сервер, весь ваш трафик
идёт через этот сервер. Вопрос «а что он там с ним делает» решается верой в
маркетинговую страницу со словами no-logs policy. Проверить нельзя — сервер не ваш.

Мы пошли от другого конца: **выходной точкой становится компьютер живого человека,
который нажал одну кнопку, чтобы помочь.** Не сервис. Не «наши сервера в 90 странах».
Чей-то VPS за три евро, домашний Synology, старый ноутбук на подоконнике или
Raspberry Pi.

Проект называется BeMyVPN — «будь моим VPN». Rust, Apache-2.0, четыре платформы,
~27 тысяч строк своего кода (плюс два форка). Под катом — как это работает внутри, три технических решения,
которыми я доволен, и честный список того, чего в нём нет.

Ссылка сразу, чтобы не искали: [github.com/mister-PARADISE/bemyvpn](https://github.com/mister-PARADISE/bemyvpn)

---

## Что вообще происходит

Три роли:

- **Хост** — тот, кто делится интернетом. Нажал «Стать хостом» — он в каталоге.
- **Гость** — тот, кому нужен доступ. Выбрал хоста из списка (или ввёл код) —
  весь IP-трафик пошёл через него.
- **Координатор** — доска объявлений. Показывает, кто сейчас раздаёт, и знакомит
  стороны. **Через него не идёт трафик. Вообще никакой, даже шифрованный.**

```
      📡 ХОСТ  ←═══ шифрованный туннель НАПРЯМУЮ ═══→  🛡 ГОСТЬ
          ↖                                          ↗
            «я раздаю!»               «кто раздаёт?»
                    ↘               ↙
                 🗂 СЕРВЕР-КООРДИНАТОР
        (только знакомит — трафик мимо него)
```

Это принципиально: координатор физически не может ни читать трафик, ни логировать
его, ни отдать по запросу — туннель строится напрямую между двумя пирами после
пробития NAT. Координатор знает, что «хост A и гость B познакомились», и на этом
его знание заканчивается. Его можно поднять свой одним бинарником — и тогда даже
это знание остаётся у вас.

Дальше — три вещи, ради которых стоит читать.

## 1. Хост не требует прав администратора. Совсем

Это главное решение в проекте, и оно определило всю архитектуру.

**Проблема.** Классическая «раздача интернета» — это IP-форвардинг. Поднять
`tun`-интерфейс, включить `net.ipv4.ip_forward`, накрутить `iptables -t nat -A
POSTROUTING -j MASQUERADE`. На Windows — ICS или RRAS. На macOS — `pfctl`. На
Android — вообще забудьте.

Всё это требует root/админа, всё это разное на каждой ОС, и всё это отпугивает
ровно того человека, которого мы хотим позвать: «просто нажми кнопку и помоги».
Никто не будет вводить sudo-пароль и править firewall, чтобы сделать доброе дело.

**Решение.** Хост не поднимает никаких интерфейсов и не трогает ядро. Он принимает
IP-пакеты гостя, **разбирает их userspace-стеком TCP/IP** и открывает наружу
**обычные сокеты** — ровно как любой браузер.

```
Гость:  приложения ОС → default route → TUN → IP-пакеты → шифр → хост
Хост:   шифр → userspace TCP/IP-стек → терминируем TCP/UDP → обычные сокеты → интернет
```

Вот и всё. Хост с точки зрения операционной системы — обычная программа, которая
открывает соединения. Как торрент-клиент. Как браузер. Никаких привилегий.

В коде это выглядит буквально так ([`crates/bmv-tunnel/src/host.rs`](https://github.com/mister-PARADISE/bemyvpn/blob/main/crates/bmv-tunnel/src/host.rs)):

```rust
//! host — выходная нода БЕЗ прав и без TUN. Работает на любой ОС.
//!
//! Принимаем IP-пакеты гостя из канала, скармливаем userspace-стеку `ipstack`.
//! Он терминирует TCP/UDP-потоки локально и отдаёт их нам как обычные потоки —
//! на каждый мы открываем НАСТОЯЩИЙ сокет к адресату и перекачиваем байты.
//!
//! Почему так: обычные сокеты есть на всех платформах, root/iptables не нужны →
//! хостом может быть сервер, ПК, Android, iOS.
```

Асимметрия получается красивая: **права нужны только гостю** (TUN-интерфейс — это
требование любой ОС, тут никуда не деться), а тот, кто помогает, не делает вообще
ничего. Причём именно эта асимметрия и нужна по смыслу: человек в свободной стране
жмёт кнопку без единого диалога, а тот, кому нужна помощь, один раз подтверждает
системный запрос на VPN.

Бонусом стек сам нарезает TCP-сегменты под MTU туннеля (у нас 1400 — оверхед
Noise ~24 + UDP 8 + IP 20 ≈ 52 байта), поэтому классических костылей с MSS clamping
не нужно вовсе.

**Цена решения — честно.** Userspace-стек медленнее ядерного форвардинга и
сложнее. Мы это знали, когда выбирали. И это вылилось в отдельную двухнедельную
историю про то, как наш TCP отдавал жалкие мегабиты — про неё будет вторая статья,
но спойлер: виноваты были 16 бит из RFC 793 и полное отсутствие congestion control
в апстриме.

Ещё цена — безопасность хоста. Раз мы открываем сокеты от его имени, гость мог бы
попросить нас сходить на `127.0.0.1`, в домашнюю сеть или на `169.254.169.254`
(привет, метаданные облака и мгновенный угон VPS). Поэтому внутренние адреса гостю
закрыты по умолчанию, и не наивным сравнением строк, а одной таблицей диапазонов на
весь клиент — включая все способы записать внутренний адрес так, чтобы он не выглядел
внутренним: `::ffff:10.0.0.1` (v4-mapped), `64:ff9b::` (NAT64), `2002::` (6to4).

Защита работает **в обе стороны**: хосту тоже закрыт доступ в домашнюю сеть гостя —
в туннель принимаются только пакеты, адресованные самому гостю. Мы не просим человека
доверять незнакомцу больше, чем необходимо.

## 2. Координатор, который нечего изымать

Координатор — это `GET /v1/ws`, один WebSocket, JSON-сообщения. Весь протокол:

```
клиент → координатор                координатор → клиенту
─────────────────────               ──────────────────────
host    {анонс хоста}               hostok | error
watch   {country?}                  dirfull {version, hosts} + дельты:
                                    diradd/dirupdate/dirremove (пушем)
connect {host_id, candidates}       connected {endpoints}; хосту: guest {candidates}
newcode                             code {code, sig}
whoami                              ip {addr}
resolve {code}                      resolved {host?}
```

Что он делает: каталог, сигналинг, STUN (как один из пула), проверка пароля
приватных сетей.
Что он **не** делает: трафик, приватные ключи, relay.

Приятная деталь: **живость хоста — это сам сокет.** Не «ttl 60 секунд», не
heartbeat-таблица в базе. Хост держит исходящее WS-соединение; закрылось — он
мгновенно исчез из каталога. Тихая смерть (мобильник уехал в метро) ловится
WS-пингом за ~8 секунд. Никакого состояния, которое надо чистить крон-джобой.
Исходящее соединение к тому же само проходит NAT — хосту не нужно ничего у себя
открывать.

Поднять свой координатор — та же одна команда, что и всё остальное. Домен, A-запись,
443-й порт. **Let's Encrypt встроен**: сертификат выпускается и продлевается сам,
`certbot` и `nginx` не нужны, почта тоже не требуется.

```bash
sudo bemyvpn server --domain твой.домен --autostart
```

Смысл в том, что дефолтный `bemyvpn.net` — это удобство, а не зависимость. Список
координаторов в конфиге — массив, не константа:

```toml
coordinators = ["https://bemyvpn.net", "https://my.coordinator.example"]
```

Заблокируют один — работает второй. Заблокируют все — остаётся ручной код, и
прямое соединение всё ещё встанет, просто без каталога.

## 3. Маскировка: три слоя, ни одного своего шифра

Протокол по умолчанию называется `noise-obfs`. Базa — Noise XX
(`Noise_XX_25519_ChaChaPoly_BLAKE2s`), тот же фреймворк и тот же ChaCha20-Poly1305,
что внутри WireGuard, через проверенную библиотеку `snow`. Своей криптографии не
пишем — это принцип, а не лень.

Транспорт у нас датаграммный, пакеты теряются и переставляются, поэтому Noise в
stateless-режиме: к каждому пакету спереди 8-байтный счётчик-nonce, как в WireGuard.

Дальше три слоя против DPI, и каждый закрывает свой отпечаток.

### Слой 1. Elligator2 — эфемерный ключ, не похожий на ключ

Первое, за что цепляется DPI в WireGuard-подобных протоколах: первые 32 байта — это
X25519-публичный ключ, а точка на кривой Curve25519 статистически отличима от
случайных байт. Ищется тривиально.

Лечится Elligator2 — отображением, которое превращает точку кривой в равномерно
распределённые 32 байта. Примерно половина ключей «представима», поэтому генерируем
в цикле, пока не повезёт:

```rust
/// ELLIGATOR2 (только маскировка). Сгенерировать ПРЕДСТАВИМЫЙ эфемерный
/// X25519-ключ: (priv[32], representative[32]). Повторяем, пока публичный ключ не
/// окажется представимым (≈50% → в среднем 2 попытки; потеря ~1 бита энтропии, на
/// стойкость не влияет). representative — равномерные 32 байта (старшие биты
/// рандомизированы tweak'ом), снаружи неотличимы от шума.
fn gen_representable_ephemeral() -> ([u8; 32], [u8; 32]) {
    use rand::Rng;
    loop {
        let mut sk = [0u8; 32];
        rand::thread_rng().fill(&mut sk);
        let tweak: u8 = rand::thread_rng().gen();
        if let Some(repr) = curve25519_elligator2::representative_from_privkey(&sk, tweak) {
            return (sk, repr);
        }
    }
}
```

Крейт — `curve25519-elligator2`, тот самый, что используется в Tor. Руками мы тут
не считаем ничего.

### Слой 2. Паддинг без общего «пола»

Второй отпечаток — размеры. Даже под шифром распределение длин пакетов узнаваемо.

Забавная история из наших же комментариев: сначала стояли фиксированные 80 байт
паддинга. Убрали — **потому что общий фиксированный пол сам стал отпечатком**.
Теперь у каждой сессии свой «пол» плюс джиттер.

Важная деталь реализации: паддинг лежит **внутри** AEAD, последним идёт байт его
длины. Снаружи никакой структуры не видно; приёмник расшифровал — прочитал
последний байт — отрезал. В коде на этом висит явное предупреждение, что вынос
паддинга наружу AEAD сломает модель, и тест, проверяющий, что длина всегда влезает
в один байт.

### Слой 3. Маскировка счётчика — как header protection в QUIC

Остаётся 8-байтный nonce в открытом виде. Это монотонный счётчик: `00 00 00 00 00
00 00 01`, `...02`, `...03`. Идеальная сигнатура — DPI ловит такое влёт, даже не
трогая шифротекст.

Поэтому шапка маскируется по образцу самого шифротекста, ровно по идее header
protection из QUIC. В проводе монотонного счётчика больше нет, кадр целиком
неотличим от случайных байт.

На этот слой есть отдельный тест, который проверяет, что замаскированная шапка не
совпадает со счётчиком **ни на одном** пакете — иначе тихая регрессия в `send`
вернула бы сигнатуру, и никто бы не заметил.

### И выбор протокола — только руками

| Имя | Что | Когда |
|---|---|---|
| `noise` | ChaCha20-Poly1305, как в WireGuard | если DPI не мешает |
| `noise-obfs` | + Elligator2 + паддинг + маскировка шапки | **по умолчанию** |
| `plain` | без шифрования | доверенная сеть, максимум скорости |

**Фолбэка нет и не будет.** Работает ровно выбранный протокол. Незнакомое имя в
конфиге не подменяется «похожим» — иначе опечатка могла бы увезти человека в `plain`,
и он бы думал, что зашифрован. Это тот класс ошибок, где «умное» поведение хуже
отказа.

## Как пробиваем NAT (и когда не пробиваем)

STUN-пул: публичные серверы плюс наш координатор как один из, а не единственный —
переживает блокировку одного домена. Дальше классический hole punching: обе стороны
через координатор обмениваются кандидатами и синхронно шлют друг другу `PUNCH`,
на чужой отвечают `PACK`.

Тонкость, на которую мы напоролись: во время фазы пробивания в сокет прилетает
всякое — поздние ответы STUN, хвосты от других кандидатов. Если принять это за
данные пира, соединение встанет не туда. Поэтому пакеты принимаются только от
адресов-кандидатов, а IP обязан совпасть с кандидатом. На это есть тест с говорящим
именем — `hole_punch_ignores_stranger_packets`.

Вторая тонкость, уже про безопасность: **адрес участника ставит сервер, а не
клиент.** Иначе можно было бы назвать чужой IP и направить пробитие NAT на него —
и вся сеть хостов превратилась бы в DDoS-отражатель. Тест на это тоже есть.

**А теперь честно про relay: его нет.** Совсем. Следствие прямое — если у обеих
сторон симметричный NAT или мобильный CGNAT, прямое соединение не встанет. Приложение
в этом случае честно говорит, что раздача из этой сети невозможна, а не крутит
спиннер.

Практический вывод: хостом должен быть тот, у кого NAT попроще. VPS с белым IP —
идеальный хост. Телефон в мобильной сети — хороший гость, плохой хост. Архитектура
relay допускает, код — нет, и я не хочу писать в README, что он есть.

## Чего в проекте нет (раздел, ради которого стоило писать)

Мне кажется, самое полезное, что может сделать автор — перечислить, где его штука не
работает. Поэтому:

**Relay нет.** Симметричный NAT с обеих сторон = нет связи. См. выше.

**Kill-switch нет.** В конфиге годами лежала ручка `kill_switch`, которая не была
реализована нигде. Мы её **удалили, а не реализовали**: настоящий рубильник — это
правила брандмауэра, застрявшее правило оставит машину вовсе без сети, а на Android
приложение его в принципе включить не может — «блокировать соединения без VPN» это
системная настройка. Делать целиком отдельным заходом либо не делать вовсе. Обещать
защиту, которой нет, — худший вариант.

**IPv6 блокируется, а не ведётся.** Туннель несёт только IPv4. Если у провайдера
есть IPv6 и его не тронуть, v6-трафик уйдёт **мимо** туннеля: на экране «Защищено»,
а настоящий адрес виден сайтам, и человек об этом не узнает. Поэтому на время сеанса
IPv6 глушится отвергающими маршрутами `::/1` + `8000::/1`, мобильные оболочки
забирают `::/0` себе, а ядро добивает v6-пакеты, которые всё же попали внутрь.
Значение `route` («вести IPv6 внутрь») в документации было и **никогда не было
реализовано** — убрали из документации.

**DNS не настраивается.** Всегда 8.8.8.8 внутри туннеля. Ручка `guest.dns` была
объявлена и не читалась никем — удалили. Причина: `system` — это ручка, *отключающая*
защиту (резолв ушёл бы провайдеру мимо туннеля, список сайтов снова у него, а на
экране «Защищено»), а выбор между `1.1.1.1` и `8.8.8.8` безвреден и бесполезен — оба
резолвит сеть хоста. Защита от подмены DNS у хоста — это DoH/DoT, отдельным заходом.

**Интерфейс только русский.** Строки лежат в коде, не в файлах локализации. Это
осознанный технический долг, и он сейчас главный ограничитель — писать об этом
на английских площадках бессмысленно, пока не вынесены строки.

**На iOS нет автообновления.** И быть не может: Apple запрещает приложениям
обновлять себя мимо App Store.

**Подписи бинарников нет.** Целостность даёт HTTPS с github.com. Отдельная подпись
защищала бы только от кражи самого аккаунта GitHub, а стоила бы офлайн-ключа и
ручной подписи каждого выпуска. На macOS это выливается в «правый клик → Открыть»
один раз — платную подпись Apple мы сознательно не покупаем.

## Что уже сделано по безопасности

Коротким списком, чтобы не растекаться:

- Сквозной Noise XX, ключи никуда не уходят; DNS всегда в туннеле.
- **Анти-повтор пакетов** — окно 64, как в IPsec. Перехваченную датаграмму нельзя
  послать заново. Отдельно больно было то, что до этого можно было переслать чужое
  «прощание» и оборвать чужую сессию.
- **Анти-угон записи хоста** — owner-токен; коды сетей подписывает только сервер (HMAC).
- **Анти-флуд координатора** — лимит WS-соединений с одного IP, потолок размера
  сообщения, потолок объявленной вместимости, ограничение темпа рассылки каталога,
  ворота на одновременные рукопожатия у хоста.
- Пароль сравнивается за постоянное время, неверный — с паузой против перебора.
- **Имя хоста по умолчанию — страна по IP, а не имя вашей машины.** В публичный
  каталог не должно уезжать `MacBook-Pro-Ivana`. Флаг и страна определяются
  **на устройстве**, по вшитой базе DB-IP — без обращения к сторонним сервисам.
- Конфиг с паролем хоста — 0600.

| Windows | `bemyvpn-windows-x86_64.exe` |
| Linux | `bemyvpn-linux-x86_64.AppImage` |

Если есть VPS и желание помочь — это две строки, и раздача переживёт выход из SSH
и перезагрузку (приложение само заводит службу systemd, имя берётся от машины,
лимит гостей подбирается по объёму памяти):

```bash
curl -fsSL https://raw.githubusercontent.com/mister-PARADISE/bemyvpn/main/install.sh | sh
sudo bemyvpn        # вкладка «Хост» → «Стать хостом»
```

Или совсем без меню, для скриптов:

```bash
sudo bemyvpn host --tunnel --autostart
```

Собрать из исходников — Rust 1.85+, `cargo build --release -p bmv-cli`.

## Зачем

Я не строю бизнес и не собираю деньги. Ни подписок, ни рекламы, ни регистрации —
и в коде негде им завестись: у координатора нет ни аккаунтов, ни платежей.

Идея простая: в мире довольно много людей, у которых есть VPS с неиспользуемым
трафиком, и довольно много людей, у которых нет доступа к половине интернета.
Между ними не хватает одной кнопки. Мы написали кнопку.

Сейчас у проекта проблема курицы и яйца в самом честном виде: **в каталоге бывает
три хоста.** Гость заходит, видит пустой список и уходит навсегда. Поэтому если у
вас есть простаивающий VPS — самое ценное, что можно сделать, это не звезда на
гитхабе, а один запущенный хост.

Код открыт целиком, Apache-2.0. Ругайте: [github.com/mister-PARADISE/bemyvpn](https://github.com/mister-PARADISE/bemyvpn)

Отдельно буду рад разбору криптослоя и модели угроз — я старался не изобретать
ничего своего, но глаз замылен, а `crates/bmv-protocol/src/noise.rs` — это ровно
тот файл, где чужой внимательный взгляд стоит дороже всего.
